# 手动验收测试方案

> 用于人工验证 v8「单任务执行」。前置：插件已重载（本次已做）。
> 执行环境：DSH 桌面 App，任意工作目录。

## 0. 先理解会被拒绝的三句话

- **不认领就改文件** → 拒绝，理由含「no active execution / 没有持有执行」。
- **还没有任务树就改文件** → 拒绝。空工作线没有任务可 claim，所以理由给出完整 bootstrap：`init` 建树 → `create` 建任务 → `claim` → 重试（这条以前是放行的，现在不放行，见 ADR-0001）。
- **团队模式的 Lead 想自己干活** → 拒绝，理由说 Lead 只协调。
- **重派别人正在跑的任务** → 拒绝，必须先中断并确认停止。

看到这四种拒绝，属于**预期**。

另外两条本次验收实测出来的边界（容易被当成 bug，其实是产品现状）：

- **卡片回答不算用户原话**：用 `ask_user_question` 选项答的内容**不能**作为授权或验收引用，只有你在聊天框里打出来的文字才算。所以验收时涉及「批准 / 验收」的回答，请直接打字。
- **未持位的 Worker 没有 shell**：A 类被拒的会话连「等几秒再重试」都做不到（`bash sleep` 也会被拒），只能用 `wait_agent` 这类 B 类工具等待。看到它反复重试却没有 shell 调用，属于预期。

## A. 标准模式（新建一个干净会话，不建任务树）

| # | 你要做的 | 预期 |
|---|---|---|
| A1 | 直接说「把 README 第一行改成 hello」 | **被拒**。这里还没有任务树，所以没有可 claim 的任务；拒绝理由应给出 `init` → `create` → `claim` → 重试的完整路径（A1b 走一遍） |
| A1b | 接着说「那就按你说的建树、建任务、claim，然后改」 | `init` / `create` / `claim` 三步成功 → **同一个改动这才落地**。**不允许**出现「这次改动很小，不用建树」的自我豁免 |
| A2 | 说「建一个任务树，然后直接改 README」 | 建树成功，但**改文件被拒**：它得先 claim |
| A3 | 接着说「先 claim 这个任务，再改」 | claim 成功 → 改文件成功 |
| A4 | 说「release，然后再改一次」 | release 成功 → **改文件再次被拒** |
| A5 | 说「claim 任务 B」（任务 A 还没结束时） | **被拒**：一个工作线只有一个执行位 |
| A6 | 交接：说「release 任务 A，分配给一个 subagent，让它 claim 后改文件」 | 交接链走通；期间 Lead 自己写文件应被拒，subagent 能写 |

**A 组看板**：任务详情里应能看到执行者与执行号；A5 被拒后树里不应出现第二个 in_progress 的「已认领」状态。

## B. 团队模式（需要一个装了 agent-team bundle 的 profile，你现在的 desktop 就是）

| # | 你要做的 | 预期 |
|---|---|---|
| B1 | 说「建一个团队任务，派给一个 worker，让它 claim 后改文件」 | worker 能写；**Lead 自己写被拒** |
| B2 | 说「你（Lead）直接跑个 bash 看看」 | **被拒**，理由说 Lead 只协调 |
| B3 | 说「把那个任务 reassign 给另一个 worker」 | **被拒**：分配只能由 claim 产生 |
| B4 | worker 完成任务后，说「让它再做另一个任务」 | **被拒**：一个 worker 实例终身只做一个任务；要换新 worker |
| B5 | 两个独立任务，派给两个 worker | 两个都能写，**并行**推进；互不阻塞 |
| B6 | 让 Lead 读文件、看任务树 | **允许**（只读与任务管理不受限） |

## C. 异常与恢复

| # | 你要做的 | 预期 |
|---|---|---|
| C1 | worker 正在跑时，说「强制释放这个任务」 | **被拒**：必须先 interrupt 并确认它已停止 |
| C2 | 先 interrupt，确认停止后再强制释放 | 成功；该 worker 再尝试写文件 → **被拒**；新 worker 可接管并拿到新执行号 |
| C3 | 把一个 worker 的会话关掉，回来看看任务 | 显示「执行者已失联」，**不给任何写权限**，任务不被自动释放 |
| C4 | 重载插件 / 重启 App 后再看任务 | 执行状态与之前一致；**不应**出现两个执行权 |

## D. 回归（这些**必须**和以前一样）

| # | 场景 | 预期 |
|---|---|---|
| D1 | 建一个 pending 任务，让它开工 | 仍然被拒：授权规则没变 |
| D2 | 交付类任务完成 | 仍然要求用户验收，agent 不能自我关闭 |
| D3 | 归档一个已授权未完成的任务 | 仍然要求 `userBasis`（用户原话） |
| D4 | 打开面板 | 任务树、详情浮层、归档区、右栏详情都正常 |
| D5 | 普通问答（不涉及文件） | 完全不受影响 |

## E. 出问题时给我什么

带上这四样，我能直接复现：
1. 会话 id（面板里能看到，或直接说哪个会话）
2. 你输入的原文
3. agent 的原始返回（尤其是那句拒绝理由）
4. 当时是标准模式还是团队模式

## F. 一句话验收标准

> 标准模式：任何时候只有一个人能改文件。
> 团队模式：Lead 只动嘴，每个 worker 只做一个任务，多个 worker 能同时干。
> 这两种约束在任何时候都不依赖 agent「自觉」——它想绕也绕不过去。
