# 0001. 任何改工作区的工具都需要一条 active execution

- **状态**：已采纳（实现见 PR `fix: every workspace write needs an execution (F)`）
- **取代**：`docs/plans/dsh-execution-scheduling-v8.md` §14「已知限制」第 4 条——「未建树的 workline 不受 A 类约束（普通问答不受影响）」。设计文档是冻结的历史记录，不改原文，以本 ADR 为准。
- **相关代码**：`host/guard.js`（门禁与拒绝文案）、`host/store.js`（同步快照）、`host/prompt.js`（无树提醒）
- **相关测试**：`test/e2e/scenarios/baseline-write.mjs`、`test/e2e/scenarios/execution-gate.mjs`、`test/tasks.mjs`
- **词汇**：见 `GLOSSARY.md` 的 class A / class B / class C、execution、claim、workline。

## 背景

v8 的执行门禁分三类工具：A 类（改工作区 / 跑代码）需要调用者在该工作线持有 `active` 执行；B 类（任务管理、执行控制）按角色授权、不需要执行；C 类（只读）永远放行。claim 从不依赖执行，所以「A 类需要 claim」不会自相矛盾。

v8 同时留了一条豁免：**工作线还没有持久化任务树时，A 类工具直接放行**。当时的理由是"普通会话不受影响"——避免给一次纯问答或一次性改动强加建树的仪式。

## 决策

**取消这条豁免。** A 类工具在没有任务树的空工作线上同样被拒绝：没有树就没有任务可 claim，也就没有任何东西能授予执行权限。拒绝走**同一条**拒绝分支，只有"出路"不同：

- 有树、无执行 → 告诉模型 `task_tree_write {"op":"claim","id":"<task>"}`。
- 无树、无执行 → 告诉模型完整 bootstrap：`init` 建树 → `create` 建任务 → `claim` 领取 → 重试这次调用。

B 类与 C 类完全不变。否则模型无法从零建立执行：拒绝自己依赖的那条路必须保持开放，claim 才能终止这个循环。

## 为什么改（真实原因）

这不是为了"更严格"而收紧，而是因为**豁免把判断权交给了被约束的一方**。

v8 落地后的手动验收里，模型接到「把 README 第一行改成 hello」这样的请求，自行把它判为 *trivial one-off, no task tree needed*，于是不建树、不 claim，直接 `write` 成功。**门禁没有被绕过——是门禁自己声明了这块不设防。** 模型只是读到了注释里的那句话，并按它行事。

任何"由发起方判断自己是否属于豁免"的规则，在模型身上都不成立：模型对自己工作的分级可以随时无成本地放宽，而这个判断本身正是门禁要消除的自由度。把入口统一成"有一条 active execution 才能写"，模型就再也无法通过自我分类进入工作区。

## 代价（如实记录）

1. **连改一个临时文件都要 claim**。新会话第一次改文件必须走 `init` → `create` → `claim` 三步。这是本次改动最容易被误解的地方：它看起来像"给一个 `echo >> tmp` 上管理流程"，实际代价是**一次性的 bootstrap**，不是每次写都重复三步；树建好之后，同一工作线的后续任务只需要 `create` + `claim`。
2. **提示词必须同步改**。无树提醒原本写着「纯问答、解释或一次性操作可跳过建树」，这句话与新规则直接冲突，也在邀请被拒绝的行为。已在 `host/prompt.js` 一并改掉；只改代码不改提示词，模型会先被提示词误导、再被门禁拒绝。
3. **拒绝文案成为产品的一部分**。空工作线的拒绝必须自带 bootstrap 序列，否则模型要么卡死，要么去猜。文案由 `denialReason({ hasTree })` 生成，并有 e2e 断言（`baseline-write`、`execution-gate`）盯着它。
4. **半读半写的工作流变重**。「顺手看一眼再改一行」现在也必须先建树，尽管那次读本身不受限。
5. **纯问答、只读工具、任务管理、goal/schedule/session 控制不受影响**；团队模式不受影响（Lead 本来就没有 A 类权限）；标准模式子代理不受影响（它们的 claim 本来就要求已分配的任务）。

## 被否决的替代方案

**A. 接受现状（保留豁免）。** 被否决：豁免正是这次事故的成因。它把"要不要受管"变成模型的一个自由判断，而模型的答案永远是"不用"。任何不改变这一点的方案都只是把事故概率留给下一次验收。

**B. 只对已批准的任务生效（有树才管，或树里已有 approved 任务才管）。** 被否决：判定权仍然留在模型手里——它只要先不建树、不批准任何任务，就回到不受管的空工作线，等于原样保留豁免；如果反过来要求"必须先有 approved 任务"，那和本方案的实际效果相同，却多了一条"先有树还是先有任务"的模糊边界和一段更绕的拒绝文案。

**C. 轻量编辑豁免（允许新建文件 / 小改动 / 临时文件）。** 被否决：必须先定义"轻量"。行数、路径、是否新建、是否在 `/tmp` 都只是代理指标，而真正的分界线是"这次改动是否值得留痕"，这又只能由发起方判断——于是豁免重新落回模型手里。而且它把门禁的覆盖面变成了一个需要长期维护、持续被试探的判据列表。更要命的是，事故里那次改动正是**一次普通的、看起来无足轻重的行编辑**。

**选定的方案 F. 取消豁免，任何写都要 claim。** 判据只剩一个，且不由模型判断：有没有 active execution。

## 结果与验证

- `test/e2e/scenarios/baseline-write.mjs`：**语义反转**并作为最基本反证——无树时 `write` 被拒、拒绝理由写出 bootstrap 路径、磁盘上没有任何文件、也没有因拒绝而凭空出现一棵树。
- `test/e2e/scenarios/execution-gate.mjs`：无树时 `write`/`bash` 被拒 → `init` + `create`（B 类无需执行）→ 无 claim 时 `write` 仍被拒 → `claim` → **同一个 `write` 调用**成功 → `release` 后 `write`/`edit`/`bash` 再次被拒且目标文件未被改动。
- `test/tasks.mjs`：门禁单测从"空工作线放行"改为"空工作线拒绝，且理由含 `init` / `create` / `claim`"，并断言另一条工作线的 claim 不会授信到空工作线。
- 文档同步：`docs/implementation-status.md`、`docs/CONTRACT.md`（不变量 14）、`docs/testing/manual-acceptance.md`（A1 预期反转）、`CHANGELOG.md`。

## 本次验收顺带暴露的两条实测限制

- **`ask_user_question` 卡片里的回答不算用户原话**，不能作为 `approvalBasis` / `acceptanceBasis` 的引用；只有用户在聊天框里打出来的文本才算。
- **未持有执行的 Worker 没有 shell**，所以它连"等一会儿再重试"都做不到，只能靠 `wait_agent` 之类的 B 类工具等待。
