# AI 任务树（摘要面板插件增强）— 需求文档

> **这是产品承诺；契约只管接口，不决定产品做什么。**

> **它是什么**：一个给人看的仪表盘——Agent 维护任务树，人在悬浮窗里 30 秒看清「最初想做什么、现在做到哪、下一步干什么」，右侧栏看详情。判断改动值不值得做，看它是否让人更容易看到这些事实。

> **不是目标（§1.3）**：不是独立的项目管理系统或团队协作平台；不是多 Agent 自动调度系统；不是人机共同编辑的任务清单；不替代代码版本控制与文件冲突保护。

> **第一版明确不做（§14）**：探索分支的自动识别、独立探索路线与分支快照/路线合并；普通会话之间的项目级任务共享；任何人工维护任务树的编辑入口；更换 Agent 后的迁移机制；多 Agent 自动调度系统；依靠任务锁实现代码隔离或文件冲突保护；桌面级悬浮窗；目标偏离的界面级提示与阻塞式确认弹窗。

> 状态：需求冻结候选（MVP）。**已实现到 v0.4.0**（`@mchenziyi/dsh-summary-panel` v0.4.0，`main` 分支）；实现现状见插件仓库 `docs/implementation-status.md`，本文档已于 2026-11-09 按实现对齐（4 处与实现矛盾的条文改成描述实现）。
> 本文只描述行为与规则，不涉及具体接口设计、存储选型与现有插件实现能力的核实。

## 1. 背景与目标

### 1.1 要解决的问题

开发周期一长，最初的方向和大纲容易被稀释：

- 中途不断被修 bug、临时需求、其他项目打断，精力被分散；
- 回来时不知道已经做过什么、停在哪里、下一步该干什么；
- 聊天记录很长，重新阅读成本高，靠回忆容易重新"猜"计划；
- Agent 在对话里答应了调整，但任务记录和后续行动没跟上。

### 1.2 目标

一个由 **Agent 持续维护、用户随时查看**的极简任务树，用来记录：

- 项目的**目标与大纲**（相对稳定，不随摘要刷新被重写）；
- **任务层级与状态**（随开发实时更新）；
- **实际进度、阻塞与下一步**（中断后能快速接上）。

它要回答两个问题：

1. 现在做的事情，还是不是最初要做的事？
2. 离开一段时间后回来，项目停在哪里、接下来做什么？

### 1.3 不是目标

- 不是独立的项目管理系统或团队协作平台；
- 不是多 Agent 自动调度系统；
- 不是人机共同编辑的任务清单；
- 不替代代码版本控制与文件冲突保护。

## 2. 实现范围与落点

| 项目 | 结论 |
|---|---|
| 实现位置 | 集成到**现有摘要面板插件**中，不另建插件、不另起开发项目 |
| 界面位置 | **DSH 界面内**，不做桌面级悬浮窗 |
| 展示分工 | 悬浮窗负责快速看进度；右侧栏负责看详情 |
| 数据范围 | 与"工作线"绑定，不按代码项目全局共享 |
| 人工维护 | 无。界面为只读，不提供编辑、拖拽排序、改状态等操作 |

## 3. 角色与职责

### 3.1 Agent 是唯一维护者

Agent 负责：

- 创建、拆分、调整任务；
- 维护任务状态、执行焦点、进度说明；
- 把用户的纠正落实到任务记录和后续行动中。

**关键约束：Agent 不能只在聊天里回应"好的"，而任务树仍保持旧方向。** 目标、优先级、当前任务的调整，必须同步落到任务树。

### 3.2 用户只查看，通过对话纠正

- 用户通过自然语言提出需求、调整方向、指出错误；
- 用户不直接编辑任务树；
- 展开/折叠属于**查看操作**，不是维护操作（见 7.3）。

### 3.3 记录是持续更新的，不是每次重建

- 摘要可以刷新，但**不得重新生成、覆盖整棵任务树**；
- 任务树是持续演进的记录，摘要只是它的一种展示形式。

### 3.4 写入时机：明确指令直接写，讨论中的提议立即写 pending

| 情形 | 是否写入 |
|---|---|
| 用户给出明确指令（新增需求、调整优先级、改变方向、纠正） | **直接写**，写入后再按新计划执行 |
| 讨论中出现一个提议、设想或备选方案 | **立即写**成 `executionApproval: "pending"` 的任务（标题 + 一句摘要），但不建子结构、不排优先级 |
| 讨论达成结论或用户明确采纳 | 把那条 pending 任务转为**已批准**，一次性补全确定的范围 |
| Agent 自己的计划调整（用户已知情或属于执行细节） | 按需写，但不得改变用户已确认的目标 |

原则：讨论中的提议当场写成 pending，结论后再转已批准——这样"它自己想扩的范围"当场可见，比事后追认更早暴露漂移。

## 4. Agent 维护任务树的触发时机

### 4.1 事件触发（及时写入）

| 触发事件 | Agent 的动作 |
|---|---|
| 用户给出明确指令 | **先更新任务树，再按新计划执行**；用户指令优先于 Agent 原有安排 |
| 开始某个任务 | 设为当前焦点、标记进行中，并写下领取记录（让面板显示谁在做） |
| 任务完成 | 自测通过后**先询问用户是否确认完成**；用户确认后标为已完成并记录结果；检查父任务状态 |
| 遇到阻塞 | 标记阻塞，记录原因与解除条件 |
| 被临时问题打断 | 记录打断关系，插入或关联临时任务，转移焦点，原任务继续保持原状态但不再处于焦点 |
| 任务被取消或暂缓 | 按 5.6 处理，记录原因 |
| 任务出现实质性进展、完成阶段性工作、切换焦点、明确暂停 | 及时保存进度与下一步 |
| 能正常感知会话结束时 | 额外记录停点（恢复不依赖这一次写入，见 4.4） |
| 讨论中出现新功能、新方向或范围变化 | 判断归属（见 6）；达到目标确认阈值时触发确认（见 12） |

### 4.2 检查点触发（先读取核对，再决定是否写入）

| 检查点 | Agent 的动作 |
|---|---|
| 会话或分支开始 | 先读取工作线的最新状态，再规划；不重写已有任务树 |
| 恢复被中断的工作前 | 确认最新状态与谁在做，避免按旧计划继续 |
| 阶段或顶层任务完成 | 对照原始目标做一次对齐检查（见 12.5） |
| 大块新工作开始前 | 判断是否触及目标确认阈值 |

### 4.3 不触发写入

- 纯粹的查询、解释、闲聊；
- 讨论过程中的提议、设想（除非已形成结论）；
- 单个工具调用或实现过程中的中间步骤，不逐条记录；
- 状态没有实际变化的重复更新。

### 4.4 不依赖"最后一次写入"的保存策略

会话不一定能可靠感知关闭事件（浏览器直接关闭、网络中断、Agent 异常终止都可能发生）。因此：

- 保存动作应发生在**任务出现实质性进展、完成阶段性工作、切换焦点、明确暂停**等时刻，而不是依赖关闭时的最后一次写入；
- 如果确实能感知到会话正常结束，可以额外记录停点，但这是补充，不是唯一保障；
- 恢复时以已保存的最新状态为准，允许最后一次未保存的微调丢失。

### 4.5 维护任务树不能妨碍开发

任务树是工作的副产物，不是额外流程：

- 只有**需要独立安排、可能中断主线、值得单独追踪**的工作，才成为任务节点；
- 顺手修好并验证过的简单问题，**记录在当前任务的进展中即可**，不必走"建任务 → 切焦点 → 修复 → 验证 → 完成 → 返回主线"的完整流程；
- 不为了维持任务树的完整性而打断正常开发节奏。

### 4.6 更新粒度

记录**有意义的进展节点**，不是操作流水账。连续多步细碎操作应合并为一条进展说明。

## 5. 任务模型

### 5.1 层级

- 任务可以有任意深度的子任务，**不人为限制层数**；
- 不要求 Agent 为了拆分而拆分，只有具备独立工作意义的步骤才成为子任务；
- 容器型父任务用于组织进度，默认不因"进行中"就锁住整个子树（见 10.2）。

### 5.2 状态

四种活跃状态，语义固定：

| 状态 | 含义 |
|---|---|
| 待开始 | 尚未开始 |
| 进行中 | 已经开始，尚未完成 |
| 阻塞 | 因外部原因无法推进，需要记录原因 |
| 已完成 | 达到预期结果、Agent 自测通过，**并经用户确认** |

不设"待验证"状态：Agent 自测通过只代表具备完成条件，**任务是否完成以用户确认为准**（见 5.7）。

暂缓不是状态，而是叠加在任务上的标记，不改变任务原有状态与进度（见 5.6）。

### 5.3 三个必须分开的概念

| 概念 | 回答的问题 |
|---|---|
| **任务状态** | 工作完成到什么程度 |
| **领取记录** | 面板上标记谁在做它（只是记录，不授予权限） |
| **当前焦点** | 此刻实际正在做哪一项 |

不能混为一谈。例如：任务状态可以是"进行中"，但当前没有执行者（会话已关闭）。

### 5.4 进度记录要求

- 记录实际做了什么、产出了什么，而不只是一个勾；
- Agent 完成工作后必须自己先验证（跑通、自测、检查），验证结论要写进进度；
- 临时插队的问题要与被打断的主线任务关联，处理后能回到原任务；
- 调整目标或计划时保留调整原因，避免无痕覆盖。

### 5.5 父子状态一致性

- 父任务还有未完成子任务时，**不能显示已完成**；
- 子任务全部完成后，若父任务仍有整体验收要求，验收通过后才能完成；
- 已完成任务不因后续修复工作被重新打开（见 6.3）。

### 5.6 取消、暂缓与归档

用户与 Agent 商量后决定不做的任务，**不物理删除，也不留在活跃树里**。

| 处理方式 | 含义 | 状态与进度 | 任务树中的表现 |
|---|---|---|---|
| **取消（归档）** | 确定不做了 | 记录取消，不再推进 | 从活跃树移除；详情中可通过"已归档"查看 |
| **暂缓** | 以后可能做，但不是当前范围 | **保留原有状态与进度**，附加"暂缓"标记 | 仍在树中，详情显示暂缓、原因、恢复条件 |

规则：

- 归档记录保留：任务名、简介、取消原因、决定时间、替代任务、已有的完成产出；
- **不物理删除的原因**：避免以后重复提议已经被否决的方案，也保留"为什么当初没做"的上下文；
- 取消父任务时，整棵子树归档；
- 取消后要复核父任务的完成条件是否仍然成立，必要时调整验收标准；
- **Agent 不擅自取消用户没同意放弃的任务**，可以建议取消，由用户确认；
- 暂缓任务保留进度，恢复后从原状态继续，**不重置为待开始**；
- 暂缓任务不主动执行，除非用户重新提出或 Agent 明确询问。

### 5.7 完成确认

任务完成遵循"Agent 判断 + 用户确认"：

1. Agent 自测通过后，判断这项工作是否已经达到用户要求；
2. 认为已完成时，**在对话中向用户确认**（例如"这个没问题了吧？可以标为完成吗"）；
3. 用户明确确认后，Agent 才把任务标为已完成，并记录完成结果；
4. 用户表示还没完成时，继续保留进行中，按反馈修改；
5. 用户之后推翻已完成的任务时，Agent 重新打开该任务（回到进行中）并记录原因；
6. 对不需要用户验收的内部工作（如临时修复、环境配置），Agent 可自行判断完成，不必逐条询问，用户仍可推翻。

判断依据由 Agent 掌握，但**"用户说没问题了"才是完成信号的最终来源**。

## 6. 任务放置规则

### 6.1 层级的含义

树的结构表达的是**包含关系与交付结构**，不是时间顺序，也不是紧急程度：

```text
目标
└── 阶段 / 模块
    └── 工作项（可独立验收）
        └── 实施步骤
```

判断标准：

- 能独立验收的，才单独成为一个任务；
- 只有一个步骤的事情，不要再拆一层；
- 层级按实际需要增加，不为"看起来整齐"而拆分。

### 6.2 讨论出的新需求或新功能

| 情况 | 放置方式 |
|---|---|
| 服务于原目标，属于已有模块 | 作为该模块的子任务 |
| 服务于原目标，但构成一个新模块 | 作为顶层任务，与既有模块同级 |
| 触及目标确认阈值（见 12.2） | **先触发目标确认**，确认后再作为新的顶层任务并记入修订记录 |
| 只改变实现方式，不改变交付内容 | 不单独建任务，属于做法层面的调整 |

### 6.3 Bug 与临时问题的放置

**基本原则：Bug 跟随所属功能归类，但已完成的父任务不因后续修复被重新打开，也不集中堆成"修复"大类。同时，简单问题不为建任务而建任务。**

| 情况 | 放置方式 |
|---|---|
| 简单问题，顺手修好并验证 | **不建任务节点**，记录到当前任务的进展中（见 4.5） |
| 任务尚未完成，Bug 属于该任务验收范围 | 优先作为该任务**未完成的工作**继续处理；确需独立安排或长期跟踪时，才拆为子任务 |
| 任务已经完成，之后发现 Bug | 在其**所属模块下创建关联修复任务**，与已完成任务建立关联；**不改变原任务已完成的状态与历史记录** |
| 与当前任务无关的紧急问题 | 与主线并列的临时任务，挂在相关模块下；标注"临时"及打断来源，处理完回到原任务 |
| 非紧急的技术债、优化项 | 挂在所属模块下，标为暂缓，不主动执行 |

约束：

- 已完成的父任务不会因为挂上修复任务而重新变成"进行中"；
- 修复任务如果影响原任务的验收标准，需要在详情中说明，而不是回滚原任务状态；
- 临时任务完成即更新状态，**不要长期滞留成容器**；
- 如果某类问题已经形成持续工作（例如系统性稳定性治理），可以升级为顶层任务，但需要用户认可。

### 6.4 讨论阶段

讨论中的提议立即记成 `executionApproval: "pending"` 的任务（只有标题与一句摘要）；达成一致后再转已批准并一次性补全范围（见 3.4）。

## 7. 悬浮窗展示

### 7.1 任务树行

每行只包含：

> **展开/折叠入口 + 状态颜色点 + 简短任务名**

- **不显示编号**；
- 用缩进表达父子关系；
- 任务名尽可能简洁，解释性内容放到悬停简介和右侧详情；
- 状态在树中**只用颜色点**表达，不显示状态文字；
- 暂缓任务整行**降低不透明度**，一眼可辨"现在不推进"；
- 颜色使用 **DSH 现有主题的语义色**，不硬编码具体色值，以适配深浅主题。

### 7.2 当前执行焦点

- 当前实际执行的任务需要突出显示，建议：**任务名加粗 + 很淡的行背景**；
- **父任务不跟随高亮**；
- "进行中"与"正在执行"不同：父任务可显示进行中，但焦点在被执行的子任务上；
- 焦点切换时同步移动；
- 暂停或结束执行后，清除执行高亮，避免误导为仍在工作；
- **多个实际执行项时允许多个高亮同时存在**（例如 Agent Team 并行），由 Lead 统一维护；
- 所有执行项**同等高亮，不区分主执行与辅助执行**。

### 7.3 默认收纳

- **首次打开 / 重新进入会话**：只展开当前执行项所需的祖先路径，其余全部收纳；
- **无任何执行焦点时**：整棵树收纳，只显示顶层任务；
- **多个执行焦点时**：展开所有焦点所在路径，可同时露出多个分支；
- **状态变化但焦点未变时**：不改变展开状态，避免界面跳动。

展开/折叠是查看操作：

- 用户可以点开分支浏览，这不属于维护任务树；
- 用户手动展开过的分支，**Agent 更新时不得强制收回**；
- 焦点切换到新任务时，自动展开新焦点路径，**之前已展开的分支保持不动**；
- 如需回到"只保留当前路径展开"的清爽状态，可由用户对话要求或 Agent 主动整理，而非每次更新重置。

### 7.4 悬停简介

鼠标悬停显示简短提示：

- 完整任务名；
- 任务简介；
- 若为阻塞状态，补充简短阻塞原因。

不在此处堆放完整日志、长历史或操作按钮。

### 7.5 面板开关与入口状态灯

**打开后常驻：**

- 点击会话头部入口按钮打开面板；
- 打开后**点击面板外部不关闭**，面板稳定停留在打开位置，不随页面滚动消失；
- 关闭方式一共四种：
  1. 再点入口按钮；
  2. 按 Esc；
  3. 点面板上的关闭按钮；
  4. **面板内的导航动作会让位**：打开文件、打开链接、打开父会话、打开子会话、打开 diff、打开任务详情时，面板自动收起——浮层会挡住导航目标，用户点完还要手动关一次才能看到结果。

**切换会话：**

- 面板不关闭，直接显示新会话所属工作线的任务树；
- 新会话还没有任务树时显示空态。

**入口状态灯（呼吸灯）：**

- 面板关闭时，入口按钮上显示一个很小的状态点，用于"瞥一眼知道在不在干活"；
- **有实际执行焦点时呼吸**（低透明度脉动），颜色跟随焦点任务状态：进行中=活跃色，阻塞=警示色；
- 没有执行焦点时不显示；
- 悬停入口按钮可看到当前执行任务名的提示；
- 尊重系统"减少动态效果"设置，开启时改为静态点、不做脉动。

## 8. 右侧栏详情

点击任务后，在右侧栏打开**只读**详情：

- 任务说明与预期结果；
- 当前状态、子任务；
- 已完成的工作、结果与验证情况；
- 阻塞原因；
- 相关调整及原因；
- 下一步。

工作线的**整体目标与大纲**也放在这里，不占用悬浮任务树空间。

此外提供：

- **已归档任务**入口，可查看被取消任务的原因与产出（**只在右侧详情里，悬浮窗不显示**）；
- **目标修订记录**，可查看原始目标、当前目标与历次修订原因。

悬浮窗与右侧栏展示**同一份数据**；打开详情不影响任务树状态。

## 9. 会话、工作线与分支

### 9.1 基本单位：工作线

- 一条工作线承载：原始目标、当前目标、任务树、进度、领取记录；
- **会话**是对话载体，不等于工作线；
- 普通新会话拥有独立工作线，不因为在同一个代码项目内就自动共享。

### 9.2 分支（第一版统一视为"接着做"）

- 从已有会话创建分支：**沿用同一条工作线、同一份任务树**；
- 分支的更新，原会话也能看到；
- 从历史消息处分支时，读取工作线的**最新任务状态**，不回退进度；
- 历史对话中的旧计划不能覆盖最新记录；
- 分支中提出换方案，视为调整当前工作线，**不自动创建独立探索路线**。

创建分支**不等于**中断原会话，也不等于转移领取记录。

### 9.3 持久保存

- 任务记录必须持久保存，刷新、重启后不丢失；
- 重新进入会话时能恢复查看对应工作线的记录；
- "不跨会话共享"不等于"不保存"。

---

## 10. 记录与接手（约定，不是锁）

目的：让人看清"谁在做哪个任务"，并在你回到旧会话或分支时不重复劳动。**它不是锁**：唯一的拒绝是 `claim` 的 compare-and-set——任务已被别人领取时，第二个 `claim` 被拒；其余写入与所有工具调用都不受"占着"影响。

### 10.1 基本规则

- **任务身份**标识记录的是哪个任务；
- **会话 ID** 标识写下记录的人；
- `claim` 是"我在做这个任务"的标记：先检查再写入，**一次原子 compare-and-set**，同一任务同一时刻只允许一个会话持有，第二个会话的 claim 被拒；
- 正常暂停或结束（`release` / 完成 / 暂缓 / 归档）都会清掉记录；
- 没有持有者校验：任何会话都可以 release 后再自己 claim；进程异常退出也不会留下"永久锁"——记录只是记录；
- 会话恢复后仍应按最新状态工作：记录不替你判断该不该继续。

### 10.2 层级与边界

- 容器型父任务不因"进行中"自动代表整个子树；
- 默认记录实际执行的那一项任务；
- 父任务本身有独立工作（如"整体联调"）时，需说明它与子任务的关系；
- 记录只解决"谁在做"的可见性，不保证不同任务修改同一文件时安全；
- 代码安全仍需依赖工作目录隔离或修改范围协调。

### 10.3 何时需要判定

- 分支创建时不必立即判定用途；
- 等分支中的 Agent 要开始实际工作时，按默认"延续"处理；
- 含义不清时，Agent 应先询问，而不是默默决定。

---

## 11. Agent Team

使用 Agent Team 时，**只由 Lead 维护任务树**——这是约定，不是校验：工具对 teammate 同样开放，但树由一个会话负责才连贯。

```text
用户提出需求或纠正
        ↓
Lead 维护任务树、安排工作
        ↓
Teammate 执行并汇报
        ↓
Lead 根据实际结果更新进度
        ↓
悬浮窗与右侧详情同步
```

规则：

- Teammate 不重组任务树；发现阻塞、完成工作或建议拆任务时，向 Lead 汇报，由 Lead 落实到树里；
- Lead 负责区分"已实现 / 待用户确认 / 已完成"；
- 团队内部委派与并行工作照常：多个任务可以同时进行，面板同时高亮；
- 若 DSH 已有团队任务板，本任务树不要求用户再维护第二份清单，两者如何关联在开发时再核实。

## 12. 目标基线与偏离确认

### 12.1 两个目标

| 概念 | 含义 | 是否可变 |
|---|---|---|
| **原始目标** | 工作线创建时确定的基线，永久保留 | 只读，永不覆盖 |
| **当前目标** | **最近一次经过确认的有效目标**，初始等于原始目标 | 可修订，但必须经用户确认 |

原始目标始终作为方向参照存在；当前目标是实际执行基准。

### 12.2 什么算"目标偏离"

只有**核心目的、主要交付结果或产品边界发生实质变化**时才需要确认。

需要确认（举例）：

- 产品定位从"内部工具"变成"对外发布"；
- 核心交付从"可用原型"变成"必须上线"；
- 主要使用场景或目标用户改变；
- 砍掉或替换一个核心模块。

**不需要确认**：

- 普通功能增减、细节调整；
- 实现细节、技术选型；
- 任务拆分方式；
- 优先级调整（除非改变成功标准）。

### 12.3 确认机制

1. Agent 察觉触及确认阈值时，**不擅自修改目标**；
2. 在对话中说明：原始目标是什么、当前目标是什么、想改成什么、为什么、影响是什么；
3. 用户明确同意后，Agent 更新当前目标，并记录修订（时间、原因、与原目标的差异）；
4. 用户不同意，**继续以当前目标为准**，Agent 恢复按当前目标执行；
5. **用户未回应时，不默认生效，继续以当前目标为准**；
6. 目标修订不宜频繁，每次修订都要有原因，避免目标被逐步漂移到无法辨认。

**关键点：未经确认的新方向不会生效，但也不会让执行回退到原始目标。**

### 12.4 以谁为准

执行基准始终是**最近一次确认过的有效目标**：

| 状态 | 执行基准 |
|---|---|
| 从未修订过 | 原始目标 |
| 修订过一次并确认 | 修订后的当前目标 |
| 再次提议修订，用户同意 | 新的当前目标 |
| 再次提议修订，用户不同意或未回应 | **保持原当前目标** |

示例：

```text
原始目标 A
→ 用户确认改为 B        （当前目标 = B）
→ Agent 提议改为 C
→ 用户不同意
→ 继续执行 B（不是 A，也不是 C）
```

原始目标 A 始终保留，可用于回答"我们最初想做什么"。

### 12.5 对齐检查的时机

- 阶段或顶层任务完成时；
- 开始一大块新工作之前；
- 长时间中断后恢复工作时；
- 用户主动询问"我们还在做原来的事吗"时。

### 12.6 界面表现

- 悬浮窗保持极简，不显示目标文本，也不为未确认的偏离增加警示标记；
- 目标、当前目标与修订记录都在右侧详情中查看。

## 13. 实时同步

### 13.1 界面侧

- Agent 更新成功后，悬浮窗与右侧详情及时同步，无需手动刷新；
- 日常更新应尽量保留用户的展开、折叠、选中与阅读位置。

### 13.2 Agent 侧

- Agent 的后续行动必须基于最新任务状态，不沿用旧安排；
- 同一个 Agent 不需要重复接收自己刚写入的更新通知。

### 13.3 关于"实时"的边界

- 不承诺瞬间中断正在运行的命令或工具调用；
- 目标是：**及时送达、在可处理的执行节点生效、不继续盲目沿用旧计划**；
- 普通记录变化**不自动唤醒**空闲会话开始开发；
- "知道变化"与"立刻开工"是两件事。

### 15.3 已识别风险与实现约束

- **浮窗是"点开才常驻"，不是常驻迷你浮层**：面板由会话头部入口按钮打开，打开后点外部不关闭，关闭方式见 7.5（四种，含导航动作让位）。"点开还是常驻"已于 2026-10-30 决策为"点开才常驻"，v0.3.7 已按此实现；若日后要求任务树"随时可见、不用点"，才需要额外做一个常驻迷你浮层或改变入口行为。
- **只读插件要扩成可写插件**：现有 Host 半只有 5 个只读 GET 路由，没有存储、没有工具；加入任务树会显著扩大插件规模。
- **写放大**：`single` 布局每次写入重写整个 JSON unit，任务节点多时成本上升；建议该域使用 `per-record` 布局。
- **依赖**：需要 `zod` + `@deepseek-ai/dsh-storage-domain`。`zod` 目前在 profile 的 node_modules 中可解析（传递依赖），但应在插件 `package.json` 显式声明。
- **父会话日志缺失**：递归找根依赖父会话持久化日志；若被删除，只能退化为当前会话作为根。
- **与团队任务板重叠**：DSH 已有 `team_task_*` 任务板（subject/description/blockedBy/owner/status），与本任务树语义部分重叠，需在实现时明确"自建树为准、不双向同步"。
- **刷新模型**：面板现有 20 秒整轮刷新；任务树需要独立的更新通道，避免与整轮刷新叠加。
- **子代理会话**：子代理也有 `parentSession`，但 `origin === 'subagent'`，需据此与分支区分。

## 16. 行为级验收要点

1. 用户说"先做 A，B 延后"后，任务树中 A、B 的状态与顺序反映该调整，而不只是聊天中回复；
2. 任务更新后，悬浮窗与右侧详情均无需手动刷新即可看到；
3. 当前执行项被突出显示，父任务不高亮；结束后高亮消失；
4. 多个并行执行项可同时高亮；
5. 树中不显示编号，状态只用主题色点，悬停可见简介与阻塞原因；
6. 默认只展开当前焦点路径，其余收纳；用户手动展开的分支不被更新收回；
7. 父任务存在未完成子任务时，无法显示为已完成；
8. Agent 自测通过但用户尚未确认时，任务仍显示进行中；用户确认后才变已完成；用户事后推翻时任务重新打开；
9. 从已有会话分支后，分支看到的是工作线最新任务状态，原会话也能看到分支的更新；
10. 分支与原会话不会同时重复执行同一任务；
11. Agent Team 中只有 Lead 更新任务树，Teammate 的改动经过 Lead 落地；
12. 刷新或重启后，任务记录仍存在；
13. 商定不做的任务从活跃树消失，原因可在归档中查到，不会被静默删除；
14. 暂缓任务保留原有状态与进度，不被重置为待开始，也不会被主动执行；
15. Agent 察觉目标偏离时先说明并等待确认，未确认前继续执行原当前目标；
16. 目标从 A 确认改为 B 后，再次提议 C 被拒绝时，执行基准保持 B；
17. 原始目标在任何阶段都能查到；
18. 与当前任务无关的紧急 bug 作为并列临时任务记录，修复后能回到原任务；
19. 已完成任务的后续 Bug 以关联修复任务处理，不改变其已完成状态；
20. 顺手修好的简单问题只记录在进展中，不强制生成任务节点；
21. 讨论中的未定方案不会被提前写进任务树；
22. 不依赖会话关闭事件，任务树也能在中断后恢复到最近一次有意义的进展；
23. 面板打开后点击外部不关闭；Esc、关闭按钮、再点入口可关闭，面板内的导航动作（打开文件 / 链接 / 父会话 / 子会话 / diff / 任务详情）也会让位收起（见 7.5）；
24. 切换会话时面板跟随显示新会话的任务树，无任务树时显示空态；
25. 有执行焦点时入口按钮显示呼吸灯，无焦点时不显示，减少动态效果时改为静态点；
26. 归档入口只出现在右侧详情，不出现在悬浮窗；
27. 暂缓任务在树上整行淡显；
28. 团队并行时多个执行项同等高亮。

## 17. 术语表

| 术语 | 含义 |
|---|---|
| 工作线 | 目标、任务树、进度、领取记录组成的记录单位 |
| 原始目标 | 工作线建立时的目标基线，永久保留、只读 |
| 当前目标 | 最近一次经过确认的有效目标，实际执行基准 |
| 会话 | 对话载体，可绑定到一条工作线 |
| 分支 | 从会话派生的新会话，第一版默认延续同一工作线 |
| 当前焦点 | 此刻实际正在做的任务，可多个 |
| 领取记录 | 某会话标记了"我在做这个任务"，面板据此显示，不授予权限 |
| 暂缓 | 保留原状态与进度的延迟标记，不改变任务状态 |
| 归档 | 已取消、从活跃树移除但保留记录的任务 |
| 容器型父任务 | 主要用于组织子任务、本身无独立执行的父任务 |
| 目标修订 | 经用户确认后，将当前目标调整为新的有效方向，并记录原因 |
| 完成确认 | 任务达到预期结果并自测通过后，由 Agent 询问、用户确认，才标记为已完成 |
| 呼吸灯 | 入口按钮上表示"当前有焦点"的脉动状态点 |

## 附录 A. 实现结构建议（核查后，非需求约束）

### A.1 Host 半新增（`index.js`）

- **域声明** `agentTaskTree`（建议 `per-record` 布局）：工作线记录（原始目标、当前目标、修订记录）、任务节点、领取记录、归档。
- **工具**：一个读取工具 + 一个"整树/子树写入"工具；写入时校验父子状态一致性，并用一次 compare-and-set 防止两个会话同时领取同一任务。
- **工作线解析**：`header.origin === 'subagent'` 视为子代理；否则沿 `header.parentSession` 递归到根，根会话 id 即工作线 id。
- **路由**：`GET /summary-panel/tasks?sessionId=`（树 + 焦点 + 占用）、`GET /summary-panel/tasks/events`（SSE，订阅 `domain/changed`）。
- **提示词**：`systemPrompt.section()` 注入维护规则（触发时机、写什么、不写什么、保持进展与下一步最新）。

### A.2 Client 半新增（`client.js`）

- 内置分区 `tasks`，`order` 小于 10，排在 Git 之前；树默认只展开当前焦点路径。
- 新增右栏 tab 类型 `summary-panel.task`，渲染只读详情（目标、进度、阻塞、验证、归档）。
- 展开/折叠与选中位置保存在客户端本地状态；Agent 更新不重置。
- 更新通道：SSE 优先，短轮询兜底；不影响其他分区的 20 秒整轮刷新。

### A.3 不做的事

- 不改动 Git / 输出内容 / 子智能体 / 来源四个既有分区的行为。
- 不与团队任务板做双向同步；团队会话下由 Lead 同时维护，以本任务树为准。
